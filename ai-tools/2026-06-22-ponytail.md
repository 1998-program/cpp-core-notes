# Ponytail — 让 AI 编码 Agent 像「最懒资深工程师」一样思考

> **项目**: [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)

## 一句话定位

Ponytail 是一套跨编码工具的 AI Agent 规则引擎，核心理念是 **YAGNI（You Aren't Gonna Need It）**——让 AI 编码助手像最懒的资深工程师一样，只写必要的代码，拒绝过度设计。

## 为什么值得关注

AI 编码助手最大的问题不是「写不出代码」，而是「写太多代码」。它会：
- 给简单需求搭出一整套类继承体系
- 为只有一个场景的功能预留扩展点
- 在 CR 里主动加「以后可能用到」的配置项

Ponytail 通过精心设计的 ruleset + hooks + MCP server，从源头约束 AI 的过度工程倾向。10 天内斩获 46K star，说明这个痛点击中了大量开发者的神经。

## 核心架构

### 1. 多工具 Rules 分发

Ponytail 同时适配 8 种主流编码工具的规则格式：

| 工具 | 规则路径 |
|------|---------|
| Claude Code | `.claude-plugin/` |
| Cursor | `.cursor/rules/` |
| Windsurf | `.windsurf/rules/` |
| Cline | `.clinerules/` |
| Codex CLI | `.codex-plugin/` |
| OpenCode | `.opencode/` |
| Kiro | `.kiro/steering/` |
| OpenClaw | `.openclaw/skills/` |

核心规则文件（如 `ponytail.md`）统一维护，通过构建脚本自动同步到各工具的格式目录。**一次编写，全工具生效**。

### 2. Hook 机制（防过度工程的前线哨兵）

`hooks/` 目录提供了 Claude Code 的 Hook 配置，在关键事件节点拦截 AI 的行为：

- **Pre-tool-use hooks**: 在 AI 即将执行文件写入/编辑操作前检查，如果检测到不必要的代码生成，直接拦截
- **Post-tool-use hooks**: 代码生成后审计，标记冗余逻辑
- **Statusline hook**: 在 Claude Code 状态栏实时显示 Ponytail 的约束状态

### 3. Ponytail MCP Server

`ponytail-mcp/` 提供了一个 MCP（Model Context Protocol）服务器，让 AI 在编码过程中可以：

- 查询当前项目的 Ponytail 约束策略
- 获取 YAGNI 合规检查
- 与规则引擎交互式地确认某段代码是否必要

MCP 协议让 Ponytail 不再只是静态规则文件，而是变成了一个**可交互的编码哲学守卫**。

### 4. Skills & Commands

- `skills/` — OpenClaw/Claude Code 的 Skill 定义
- `commands/` — `/ponytail-gain` 等自定义命令，提供**量化的影响评估记分板**，让你看到应用 Ponytail 规则后减少了多少冗余代码

## 核心使用场景

### 场景 1：新项目初始化——从第一天就拒绝过度设计

```bash
# 一键安装 Ponytail 到你的项目
npx ponytail init
# 或手动拷贝 .cursor/rules/、.claude-plugin/ 等到项目根目录
```

初始化后，当你对 Cursor/Claude Code 说「帮我加个用户登录功能」时，AI 不会再帮你搭什么 `AbstractAuthStrategy` 工厂模式，而是直接给你一个最简可用的登录实现。

### 场景 2：Code Review 辅助——自动检测过度工程

在已有项目中引入 Ponytail，AI 在 review 代码时会自动标注：
- 🔴 **Over-engineered**: 不必要的抽象层、未使用的配置项、过早优化
- 🟡 **YAGNI borderline**: 当前不需要但未来可能需要的扩展点
- 🟢 **Lean & clean**: 刚好够用的实现

### 场景 3：团队规范统一——同一套规则跨工具生效

团队中有人用 Cursor，有人用 Claude Code，有人用 Windsurf？Ponytail 的多工具分发机制确保所有人受到相同的约束，不会因为工具不同而产生代码风格差异。

## 快速上手

```bash
# 方式 1：npx 一键安装
npx ponytail init

# 方式 2：手动拷贝规则文件
git clone https://github.com/DietrichGebert/ponytail.git
cp -r ponytail/.cursor/rules/ your-project/.cursor/rules/
cp -r ponytail/.claude-plugin/ your-project/.claude-plugin/

# 方式 3：MCP Server（需要 Node.js）
cd ponytail/ponytail-mcp
npm install
node server.js
# 然后在 Claude Code 的 MCP 配置中添加此服务
```

## 设计哲学解析

Ponytail 的名字暗示了「马尾辫」——简洁、利落、不拖泥带水。其规则体系围绕三条核心原则：

1. **最简实现优先**: 如果一段代码能删掉且不影响功能，它就不该存在
2. **延迟抽象**: 至少出现三次重复再考虑抽象，而不是「预防性」地设计接口
3. **拒绝配置膨胀**: 能硬编码就硬编码，不要为想象中的未来用户预留配置项

这与传统软件工程中「设计先行」的理念形成有趣张力——在 AI 编码时代，**过度设计的成本远高于重构的成本**，因为 AI 可以在需要时瞬间重构。

## 与同类项目的对比

| 项目 | 定位 | 工具覆盖 | 交互性 |
|------|------|---------|--------|
| **Ponytail** | YAGNI 约束引擎 | 8 种工具 | MCP 交互 + Hook 拦截 |
| wshobson/agents | 多工具 Agent 插件市场 | 6 种工具 | 静态规则 |
| agency-agents-zh | 中文 AI 专家角色库 | 18 种工具 | 静态角色 |

Ponytail 的独特之处在于它不提供「让 AI 做更多」的能力，而是**让 AI 做得更少但更精准**。在 AI 编码工具拼命堆功能的当下，这种减法哲学反而更稀缺。

## 实用建议

1. **渐进式引入**: 不要一次性全量启用所有规则，先用最核心的 YAGNI 规则，观察一周后再加更多约束
2. **配合 Code Review 使用**: 把 Ponytail 的检测输出纳入 CR 流程，而非完全自动化
3. **定期调参**: `/ponytail-gain` 命令的能量计分板可以帮助你判断约束是否过紧或过松
4. **MCP 模式适合大型项目**: 小项目用静态规则足够，大项目才值得启动 MCP Server 获得交互式约束
