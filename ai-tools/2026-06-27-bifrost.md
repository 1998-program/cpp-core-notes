# Bifrost — 11µs 开销的企业级 AI Gateway（OpenAI 兼容 + 多 Provider 故障转移 + MCP）

> 仓库：[maximhq/bifrost](https://github.com/maximhq/bifrost) · ⭐ 6.0k · Go · Apache-2.0
> 一句话：把 23+ LLM 厂商（OpenAI / Anthropic / Bedrock / Vertex / Cohere / Groq / Ollama …）藏在一个 OpenAI 兼容端点后面，5k RPS 持续压测时 P50 仅给请求加 **11µs** 开销，自带故障转移、负载均衡、语义缓存、MCP 工具网关。
> 推送日期：2026-06-27 · 类目：AI Gateway / LLM Proxy

---

## 1. 它到底是什么

Bifrost 是一个**用 Go 写的高性能 LLM 反向代理（Gateway）**，定位是 LiteLLM 的「企业级、性能优先」替代品。和 LiteLLM（Python，单 RPS 加 100ms+）相比，Bifrost 把代理路径写成纯 Go 异步队列，官方在 t3.xlarge 上跑 5k RPS 持续压测时，单请求额外开销只有 11µs、队列等待 1.67µs、API key 加权选择 ~10ns。

它做的事情**只有一件**：在你的应用 ↔ 多家 LLM Provider 之间，做一层「永不宕机的多路通道」。

```
Your App ──▶ Bifrost (:8080) ──┬─▶ OpenAI
                                ├─▶ Anthropic
   OpenAI-compatible            ├─▶ AWS Bedrock
   /v1/chat/completions         ├─▶ Google Vertex
                                ├─▶ Ollama (local)
                                └─▶ ... 23+ providers
```

启动只要一行：

```bash
npx -y @maximhq/bifrost
# 或者
docker run -p 8080:8080 -v $(pwd)/data:/app/data maximhq/bifrost
```

零配置就能跑起来——它会启动一个 Web UI（`http://localhost:8080`）让你在浏览器里加 API key、配置 fallback 链、看实时 metrics。

## 2. 最核心的使用场景

Bifrost 不是一个「玩具网关」，它解决的是**生产环境跑 LLM 三个绕不开的痛**：

### 场景 A：多 Provider 故障转移（Never Go Down）

最直接、也是最高频的用法。线上服务调 OpenAI，OpenAI 5xx / rate-limit / 区域不可用时，自动切到 Anthropic / Bedrock，调用方代码一行不改。

```bash
# 业务代码里只需要把 base_url 改一下
- base_url = "https://api.openai.com"
+ base_url = "http://bifrost:8080/openai"
```

在 Bifrost 的配置里挂一个 fallback 链：

```json
{
  "providers": {
    "openai":    { "keys": ["sk-..."], "weight": 100 },
    "anthropic": { "keys": ["sk-ant-..."], "weight": 0 },
    "bedrock":   { "region": "us-east-1", "weight": 0 }
  },
  "fallbacks": {
    "openai/gpt-4o": ["anthropic/claude-3.5-sonnet", "bedrock/claude-3.5-sonnet"]
  },
  "retry": { "max_attempts": 3, "backoff_ms": 200 }
}
```

调用方拿到的是统一的 OpenAI 协议 response，**完全感知不到底下换了厂商**（Bifrost 在内部把 Anthropic 的 messages API 翻译成 OpenAI 格式）。这一点是它打 LiteLLM 的核心卖点。

### 场景 B：多团队成本治理（Virtual Keys + Budget）

公司里 10 个团队都要用 LLM，每个团队按月预算划分、按部门做 rate-limit、按用户记账——这件事用 OpenAI 原生 API key 根本做不了。

Bifrost 提供**Virtual Keys**：你创建一个内部 vk_xxx，绑定到某个真实 Provider key，再挂上 budget / rate-limit / 允许的模型白名单：

```json
{
  "virtual_keys": [
    {
      "key": "vk_team_search",
      "provider_key": "openai_main",
      "monthly_budget_usd": 2000,
      "rate_limit_rpm": 600,
      "allowed_models": ["gpt-4o-mini", "gpt-4o"]
    },
    {
      "key": "vk_team_rec",
      "provider_key": "anthropic_main",
      "monthly_budget_usd": 5000,
      "rate_limit_rpm": 1200,
      "allowed_models": ["claude-3.5-sonnet", "claude-3-haiku"]
    }
  ]
}
```

Bifrost 自带 Prometheus metrics 和 OIDC 用户体系，把「谁花了多少钱」做成内部账单是开箱即用的。

### 场景 C：MCP Gateway（让模型用上你的内网工具）

这是 Bifrost 区别于其他 gateway 的杀手锏。它不仅是 LLM 反向代理，还内嵌了一个 **MCP（Model Context Protocol）网关**：你在 Bifrost 里挂载若干 MCP server（filesystem、web-search、内部数据库），然后**任何走 Bifrost 的 LLM 调用都自动获得 tool-calling 能力**——上游应用不需要关心 MCP 协议，只要正常发 chat completion，Bifrost 在 server-side 完成 tool routing 和多轮 ReAct。

```yaml
mcp:
  servers:
    - name: filesystem
      command: ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/data"]
    - name: company-search
      url: "http://internal-search.svc:9000/mcp"
      auth: { type: bearer, token_env: COMPANY_SEARCH_TOKEN }
```

业务侧只要：

```python
client = OpenAI(base_url="http://bifrost:8080/openai")
resp = client.chat.completions.create(
    model="openai/gpt-4o",
    messages=[{"role": "user", "content": "查一下 K1-F3 楼层昨天的访客记录"}],
    # 不用传 tools，Bifrost 自动注入挂载的 MCP server 工具
)
```

模型在 Bifrost 内部跑完整个 tool-call 闭环，应用拿到最终自然语言答案。这对**老应用想升级成 Agent**几乎是零侵入。

### 场景 D：语义缓存削峰省钱

Bifrost 内置 vector store 接入（Redis-VSS / Qdrant / pgvector），可以按 embedding 相似度命中历史响应。对 RAG / 客服 / 重复 prompt 类业务，命中率 30-60% 是常见值，直接砍掉对应比例的 token 账单：

```json
{
  "semantic_cache": {
    "enabled": true,
    "store": "qdrant",
    "qdrant_url": "http://qdrant:6333",
    "similarity_threshold": 0.92,
    "ttl_seconds": 86400,
    "max_cache_size": 100000
  }
}
```

## 3. 为什么是 Go：性能基线对比

| 指标（5k RPS, t3.xlarge） | LiteLLM (Python) | Bifrost (Go) |
|---|---|---|
| 单请求额外开销 | ~5-20 ms | **11 µs** |
| 队列平均等待 | 数毫秒 | **1.67 µs** |
| API key 加权选择 | 微秒级 | **~10 ns** |
| 5k RPS 成功率 | 受 GIL 影响掉点 | **100%** |
| 内存占用（idle） | 200-400 MB | ~40 MB |

Bifrost 把热路径做成完全 lock-free：
- API key 选择用预生成的别名采样表（Alias method），O(1) + ~10ns
- 请求队列用 Go channel + worker pool，避免 mutex
- Provider 翻译层（OpenAI ↔ Anthropic 协议）用代码生成而非反射

对**百度内部 RPC 同学**来说，这套思路和 brpc 的 bthread + butex 用户态调度同源——把网络转发和协议翻译这种 IO-bound 工作压在尽量短的关键路径上。

## 4. 部署形态：3 种选择

### 4.1 HTTP Gateway（推荐生产）

```bash
docker run -d \
  -p 8080:8080 \
  -v $(pwd)/config.json:/app/data/config.json \
  -e OPENAI_API_KEY=sk-... \
  -e ANTHROPIC_API_KEY=sk-ant-... \
  --name bifrost \
  maximhq/bifrost
```

业务侧改 base_url 即可。

### 4.2 Go SDK 嵌入（极致性能）

如果你的应用本身是 Go 写的，可以把 Bifrost 当库嵌入，省掉一层网络跳转：

```go
import "github.com/maximhq/bifrost/core"

client, _ := bifrost.New(&bifrost.Config{
    Providers: map[string]bifrost.Provider{
        "openai":    {Keys: []string{os.Getenv("OPENAI_API_KEY")}},
        "anthropic": {Keys: []string{os.Getenv("ANTHROPIC_API_KEY")}},
    },
    Fallbacks: map[string][]string{
        "openai/gpt-4o": {"anthropic/claude-3.5-sonnet"},
    },
})

resp, err := client.ChatCompletion(ctx, &bifrost.Request{
    Model: "openai/gpt-4o",
    Messages: []bifrost.Message{{Role: "user", Content: "hi"}},
})
```

### 4.3 K8s 集群模式（多节点）

企业版支持多副本 cluster mode，节点之间共享 budget / cache / rate-limit 状态（基于 Redis 或 etcd）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: bifrost }
spec:
  replicas: 6
  template:
    spec:
      containers:
        - name: bifrost
          image: maximhq/bifrost:latest
          env:
            - { name: BIFROST_CLUSTER_REDIS, value: "redis://bifrost-redis:6379" }
            - { name: BIFROST_CLUSTER_NODE_ID, valueFrom: { fieldRef: { fieldPath: metadata.name } } }
```

## 5. 协议翻译细节（这层是 Bifrost 的精华）

Bifrost 内部维护**统一中间表示（IR）**：所有上游协议先翻译成 IR，再翻译到下游 Provider 的原生协议。

```text
Client OpenAI request
        │
        ▼
   Bifrost IR  ◀──┐
        │         │ (跨 Provider 转换)
        ▼         │
  Anthropic API ──┘
        │
        ▼
   Bifrost IR
        │
        ▼
Client OpenAI response
```

关键的兼容点：
- **tool_calls**：OpenAI 的 `tool_calls[]` ↔ Anthropic 的 `content[].type=tool_use` 双向翻译
- **streaming**：SSE chunk 重写为统一 `delta` 格式
- **多模态**：OpenAI `image_url` ↔ Anthropic `source.type=base64`
- **system message**：Anthropic 单独的 `system` 字段 ↔ OpenAI 的 `role:system`

对老应用来说效果是「一段代码服务所有模型」。

## 6. 上手 30 分钟做的 4 件事

1. **跑起来**：`npx -y @maximhq/bifrost`，浏览器开 `localhost:8080`。
2. **加 Provider**：UI 左边加 OpenAI / Anthropic key，自动测试连通性。
3. **配 fallback**：把 `openai/gpt-4o` 的 fallback 设成 `anthropic/claude-3.5-sonnet`，UI 上点几下就能保存。
4. **改业务代码**：把 OpenAI SDK 的 `base_url` 改成 `http://localhost:8080/openai`，跑一次。然后**手动 revoke 你的 OpenAI key**，再跑一次，会看到请求自动落到 Anthropic，业务无感。

这个 demo 跑完，你就理解了它的全部价值。

## 7. 适合 / 不适合

✅ **适合**
- 已经在用 LiteLLM 但被性能/Python GIL 拖累
- 需要多 Provider 故障转移、企业级预算管控
- 想给老应用零侵入加 MCP / tool-calling 能力
- 调用 LLM 的 QPS > 100，对延迟敏感

❌ **不适合**
- 只调一家 Provider 且没有可用性要求 → 直连即可
- 团队没人懂 Go，且没需求自定义 plugin → 用 LiteLLM 也够
- 想要把 Bifrost 当 RAG / Agent 框架 → 错位，那是 LangGraph / AgentScope 的事
